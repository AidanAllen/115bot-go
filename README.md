# 115bot-go

115 网盘自动化工具的 Telegram 机器人端，Go 实现。内存优先设计，单二进制部署。

## 为什么是 Go

在与目标机器同配置（953MB 内存、swap 已用 520MB）的服务器上实测：

| 指标 | Java 17 + Spring Boot（原方案） | 本项目 Go |
|---|---|---|
| 闲置常驻 | 72 MB | **8.0 MB** |
| 峰值 | 328 MB | **9.3 MB** |
| OS 线程 | 35 | 7 |
| 交付物 | 镜像 323 MB | 单二进制 9.4 MB |

数据为真实进程 `/proc/<pid>/status` 采样，非估算。

## 已实现功能

| # | 功能 | 命令 |
|---|---|---|
| 1 | 磁力链 / ed2k 离线下载（发送即识别） | 直接发送链接 |
| 2 | 视频 / 文件转存到 115 | `/d` |
| 3 | 扫码登录 115（按钮选设备） | `/login` |
| 4 | 设置 cookie、UA、转存通道 | `/cookie` `/ua` `/channel` |
| 5 | 检查 115 登录状态 | `/checklogin` |
| 6 | 设置转存目录 / 离线目录 cid | `/transfercid` `/setcid` |
| 7 | 账号初始化（一键体检） | `/initaccount` |
| 8 | 总开关 / 获取 id / 绑定 id / 版本 / 运行状态 | `/s` `/id` `/setid` `/v` `/state` |

附带：`/start` / `/set115` 图形化设置菜单、`/cancel` 取消输入、`/help`。

**不需要记命令**：启动时机器人会把全部命令注册到 Telegram，在输入框打 `/` 就弹出带说明的列表；
`/help` 下方每条命令都有一个按钮，点一下即执行；扫码登录的设备类型也是按钮选择。

**点进去就出得来**：UA 档位、转存通道、登录设备、目录浏览器、全部命令这些二级面板，
底部都带「⬅️ 返回上一层」，就地退回 115 设置菜单，不用重新敲命令。

## 快速开始

**方式 A（推荐，服务器上无需拉 Go 工具链）**：本机交叉编译出静态二进制，再打包成运行镜像。

```bash
make VERSION=0.1.4 linux            # 产出 bin/115bot-linux-amd64
```

把 `docker-compose.yml`、`Dockerfile.runtime`、`.dockerignore`、`bin/115bot-linux-amd64`、`.env`
上传到服务器同一目录（`Dockerfile.runtime` 只把这一个二进制送进构建上下文，镜像约 30MB），然后：

```bash
mkdir -p data && chown -R 10001:10001 data   # 容器以 uid 10001 运行，目录属主必须先对齐
chmod 600 .env
docker compose up -d --build
```

**方式 B**：服务器直接从源码构建（会拉 `golang:1.23-alpine` 并执行 `go mod download`），
把 `docker-compose.yml` 里的 `dockerfile: Dockerfile.runtime` 改成 `Dockerfile` 即可。

验证：

```bash
docker compose logs -f                                  # 应看到「机器人已启动」
docker run --rm --env-file .env -v "$PWD/data:/app/data" \
  hi_115bot:latest --check-cookie                       # 校验 115 登录态
docker stats hi_115bot --no-stream                      # 常驻内存约 7MB
```

或直接运行：

```bash
make build
./bin/115bot
```

### 每次更新：一键部署（含清理上一版遗留）

```bash
./scripts/deploy.sh 0.2.4      # 或 make deploy VERSION=0.2.4
SKIP_TESTS=1 ./scripts/deploy.sh 0.2.4    # 跳过 vet/test 直接发
CLEAN_ONLY=1 ./scripts/deploy.sh 0.2.4    # 只上传 + 清理，不重建容器
```

它依次做：本机 `go vet` + `go test` → 交叉编译 → 上传二进制与编排文件 →
服务器上 `sqlite3 .backup` 备份数据库 → 换二进制 → `docker compose up -d --build` →
**删除上一版遗留**，最后打印镜像/容器状态和最近日志。

清理范围（只针对新版 115bot，不碰老 Java 版 `115bot` 容器，也不碰其他应用）：

| 遗留物 | 说明 |
|---|---|
| 旧 `hi_115bot` 镜像 | 每次重建都会把上一个 `:latest` 挤成 `<none>` 悬空镜像，约 30MB/个。按「悬空 + 入口是 `/app/115bot`」识别后删除，不会误伤别的应用的悬空镜像 |
| 源码构建残留 | 早期源码部署留下的 `src/`、`Dockerfile`、`go.mod`、`go.sum`、`Makefile`、`.gitignore`（现在只用 `Dockerfile.runtime`，都不需要） |
| 过期数据库备份 | `data/115bot.db.bak-*` 只保留最近 5 份 |
| 过期临时文件 | `data/tmp` 下超过 24 小时的文件（正常任务用完即删，这里只兜底） |

服务器上的脚本也可单独执行：

```bash
VERSION=0.2.4 sh /home/docker/docker-compose/hi_115bot/scripts/deploy-remote.sh
```

## 谁能用：多用户 + 各自独立的 115 账号

**任何 Telegram 用户都可以使用这个机器人**，但**每个人必须登录自己的 115**——
没登录 115 的人用不了转存和离线下载，会收到引导去 `/login`。

- 115 凭据（cookie / UA / 转存通道 / 转存目录 / 离线目录 / 功能开关）**按用户隔离**，
  存在 `user_config` 表里，主键是 `(user_id, key)`。A 的文件只会进 A 的网盘，任务记录也各看各的。
- 群聊里按钮作用于**点按钮的人**，不是消息的主人：A 开的菜单、B 点「设置 ua」，改的是 B 的配置。
- `bot.ownerId` 只标记「机器人归谁」（供以后的 web 控制台做用户管理），**不限制谁可以使用**。
  它来自 `OWNER_ID` 环境变量，或首次 `/id` 点「绑定为我」的人。
- 从单用户版本升级时，启动时会自动把旧的全局 `account.*` 迁移到 owner 名下并清掉全局键（幂等），
  已登录的 115 会话不需要重新扫码。

首次使用：给机器人发 `/login` 扫码登录你自己的 115，然后 `/set115` 打开设置菜单。

### 下载与转存

| 操作 | 说明 |
|---|---|
| 直接发送磁力链 / ed2k | 自动提取并下发离线下载，支持单条与多条混发、转发消息 |
| 直接发 `/d` | **自动转存开关**：开启后发过来的每个文件自动进 115，不用再逐条回复 |
| 回复某条消息后发 `/d` | 只转存那一条（回复 + `/d 新文件名` 可顺手改名） |
| 直接发视频 / 图片 / 文件 | 开关打开时自动转存；进度消息回复在你的原消息下面 |

自动转存支持**视频、图片、照片、文档、音频、GIF、视频笔记**（照片取最大的一张）。
多个文件会进入队列串行处理（跨境上行只有一条链路），回复里会告诉你排在第几位。

#### 转存后的文件名怎么来的

按这个顺序取，取到即用：

1. **手动改名**：回复某条消息发 `/d 新名字`
2. **消息说明文字（caption）**：发文件时写在说明框里的内容，取第一行
   - 说明里没扩展名就按类型补（视频 `.mp4`、照片 `.jpg`、文档沿用原扩展名）
   - 说明本身就是链接（网址 / `magnet:` / `ed2k:`）时**不当文件名**
3. **TG 原文件名**：手机相册常是 `1月12日 (5)(1).mp4` 这种，可用性一般
4. **兜底**：`photo_<unique_id>.jpg` / `video_<unique_id>.mp4`

同名文件自动排开：`名字.mp4`、`名字(1).mp4`、`名字(2).mp4`……（按「用户 + 转存目录」判断，
历史任务里出现过或正在排队的名字都算已占用）。这样网盘里不会互相顶掉，也不会被 115 悄悄改名。

```
cmd/bot/main.go          进程入口、配置加载、优雅退出、--check-cookie CLI
internal/config          环境变量加载与启动期校验（快速失败）
internal/store           SQLite 持久化：配置表 + 任务表（WAL 模式）

  ├─ qrlogin.go          扫码登录（多地址降级、cookie 双形态解析）
  ├─ files.go            目录列表与路径解析
  ├─ offline.go          离线下发/查询/删除、目录校验
  ├─ auth.go             登录态校验
  ├─ cipher.go           上传加密层（AES-CBC / k_ec / LZ4 解压）

  └─ validate.go         链接提取、cookie / cid / UA 校验
internal/bot             Telegram 层
  ├─ commands.go         命令表（唯一来源：TG 菜单 + /help 正文 + /help 按钮）
  ├─ router.go           消息与回调分发
  ├─ session.go          两步式输入状态机（带 TTL）
  ├─ menu.go             内联键盘
  ├─ texts.go            全部用户可见文案
  ├─ cmd_login.go        扫码登录
  ├─ cmd_general.go      基础命令
  ├─ cmd_account.go      账号与目录
  ├─ cmd_offline.go      离线下载与转存
  └─ scripts/smoke_bot.py 本地 TG 模拟器，自动遍历所有按钮
```

**关键设计**

- 配置全部来自环境变量，启动时集中校验，缺项立即失败并给出中文原因。
- 115 接口地址集中于 `endpoints` 结构体，可整体替换（测试即用此注入 mock）。
- 客户端按调用时读取配置构造，改 cookie 后立即生效，无需重启。
- 每个更新在独立 goroutine 处理（上限 4 个并发）：一次几小时的 `/d` 上传不会堵住长轮询，
  期间 `/state`、`/cancel` 仍可用。
- 转存走**队列串行**（上限 64）：自动转存可能一次涌进多个文件，排队保证不丢也不互相抢带宽；
  队列用独立的后台 worker 消费，上传上下文与某次 update 解绑，几小时的大文件不会被提前取消。
- 两步式输入有 TTL 且一次消费即失效，不会出现状态残留。
- 错误分类型：登录失效、API 业务错误、网络错误分别映射为不同文案。

## `/d` 转存的上传通道

`/d` 走 115 网页通道：只要扫码登录即可完成**真实上传**（不只是秒传），不需要申请任何第三方 token。

### 可切换的转存通道

通道只有一套实现（下面的链路），差别在于**向 115 声明的客户端身份**：`appversion`（参与 token 签名）
和 `UA`。两者必须成对，所以做成一体化的选项，由 `/channel` 面板点选。

| 标识 | 通道 | appversion | 适用会话 |
|---|---|---|---|
| `web` | 115 网页通道（默认） | 36.2.28 | 默认，跑通次数最多 |
| `app` | 115 App 通道 | 30.5.1 | 以 App 客户端身份上传 |
| `alipaymini` | 支付宝小程序通道 | 30.5.1 | 支付宝扫码登录时配套 |
| `wechatmini` | 微信小程序通道 | 30.5.1 | 微信小程序登录时配套 |

四条都在真实账号上做过端到端验证（传 4KB 随机文件到拿到 `pick_code`，随后移入回收站清理），
握手返回 `status=1`（需要真实上传）说明该组合被服务端认可。
默认通道沿用历史上跑通过大文件的组合，`channel_test.go` 里钉死了它的取值，防止被误改。

### 完整链路（已实测跑通）

```
1. GET  proapi.115.com/app/uploadinfo        → user_id + userkey（字段平铺在顶层）
2. POST uplb.115.com/4.0/initupload.php?k_ec= → 加密封装，见下
       status=2  秒传成功（云端已有同一文件）
       status=7  需按字节区间做二次校验，算 SHA1 后重试
       status=1  需要真实上传，返回 bucket / object / callback
3. GET  uplb.115.com/3.0/gettoken.php         → 阿里云 STS 临时凭据（无需认证）
4. GET  uplb.115.com/3.0/getuploadinfo.php    → OSS 接入点
5. PUT  <bucket>.oss-cn-shenzhen.aliyuncs.com/<object> → OSS V1 签名上传
6. OSS 触发 115 的 completeupload 回调 → 文件入库，返回 pick_code
```

### 关于 4.0 接口的加密

`initupload.php` 的请求体是 **AES-128-CBC 加密**，响应是**加密后再 LZ4 分块压缩**。
它看起来像"专有加密"，但实际上：

- `AES_PUBKEY` / `AES_KEY` / `AES_IV` 都是**硬编码常量**，没有真正的密钥协商
- `k_ec` 只是"固定公钥 + 时间戳 + CRC32"再 base64
- 响应解压是标准 LZ4 block 格式

因此可以完整复刻，本项目在 `cipher.go` 里手写实现（含 LZ4 解码，零外部依赖），
并用 openssl 生成的密文做了逐字节比对测试。

### 为什么不走分片

OSS 单次 PUT 上限 5GB，本项目 **5GB 以内一律走单 PUT**。

分片上传能成功传完、也能合并，但 115 的 `completeupload.php` 会返回
`errno=10002 校验文件失败`——OSS 回调模板里的 `${sha1}` 在分片模式拿不到整体 SHA1，
而回调 body 由 115 固定给出、无法修改。分片代码保留并有测试覆盖，但默认不启用；
文件超过 5GB 时会明确报错，而不是悄悄失败。

### 速度提示（重要）

实测（2026-10-29，日本节点 → 115 的阿里云深圳 `oss-cn-shenzhen.aliyuncs.com`）：

| 场景 | 实测 |
|---|---|
| 真实上传 10 MB | **316.7 s，约 32 KB/s** |
| 同一文件再传一次（秒传） | **2.4 s**（`status=2`，不传数据） |
| 真实上传 23.5 MB 视频 | 900 s，约 26 KB/s |
| 同一台机器到境外公共端点上传 5 MB | 1.8 MB/s |
| 同一台机器从阿里云镜像下载 | 6.0 MB/s |

**瓶颈是跨境链路的丢包，不是代码、也不是 115 限速**：到 OSS 接入点 `ping` 20 包丢 3 包
（**15% 丢包**，RTT 约 105ms）。按 Mathis 公式 `吞吐 ≈ MSS / (RTT·√p)` 估算约 37 KB/s，
与实测 32 KB/s 吻合——这种丢包率下任何单条 TCP 都跑不快，换语言、换并发都一样
（分片并行能绕开，但 115 的回调校验不接受分片，见上文）。

因此：

- **秒传才是最快的路**：命中时 2 秒完成，`/d` 最有价值的场景。命中条件是 115 云端已有
  同 SHA1+大小的文件（热门资源、转存过的内容都会命中；自己拍的原创视频不会）
- **没命中秒传就要真传**，1GB 视频约 3~9 小时，且晚高峰（北京时间 21~23 点）跨境丢包最严重
- 大文件建议优先用磁力/ed2k 离线下载（由 115 服务器自己拉，不受本机上行限制）
- 想彻底解决只能换出口：部署在到阿里云深圳丢包低的机器上（国内 / 香港），或走一条更稳的隧道

上传超时会按文件大小自动估算（按 30KB/s 悲观速率），不会因固定超时误杀大文件；
转存成功的回复里会带**本次实测平均速度**，慢的时候能一眼看出是链路限速还是卡住了。

## 配置项

见 `.env.example`。重点项：

| 变量 | 必填 | 说明 |
|---|---|---|
| `BOT_TOKEN` | ✅ | Telegram Bot Token |
| `OWNER_ID` | | 机器人所有者 id（用于后续 web 控制台），留空则首个 `/setid` 生效；**不填也不影响任何用户使用** |
| `TG_API_ENDPOINT` | | 本地 Bot API 端点（收发 >20MB 文件时必须配置） |
| `OFFLINE_CID` / `TRANSFER_CID` | | ⚠️ **多用户部署必须留空**。它们是「该用户尚未设置目录时的兜底」，不是你的默认目录；填上后陌生用户会拿着自己的 cookie 往你的 cid 传，而那个 cid 在他网盘里不存在 |
| `DEFAULT_UA` / `UPLOAD_CHANNEL` | | 同理是兜底值，留空走内置默认。UA 与扫码会话不匹配会导致 115 判定异常设备掉线，别乱填 |
| `MAX_DOWNLOAD_BYTES` | | 单文件下载上限，0 为不限 |
| `POLL_TIMEOUT` / `HTTP_TIMEOUT` / `LOG_LEVEL` / `DB_PATH` / `TEMP_DIR` | | 均有内置默认（60s / 30s / info / `./data/115bot.db` / `./data/tmp`），不需要显式写 |

> v0.2.0 起 cookie、UA、转存通道、转存目录、离线目录、功能开关、任务记录**全部按用户存储在数据库**，

## 已知限制

1. **已与真实账号联调**（登录态、目录、离线配额与任务列表、离线下发/删除均已实测通过）。踩到并修正的主要问题：`task_lists`/`files` 成功响应不带 `state`、`category/get` 字段平铺而非 `data` 包装、`add_task_urls` 的参数是 `url[0]` 而不是 `urls`、扫码返回的 `cookie` 是对象而非字符串。
2. 115 会话与出口 IP 绑定，机器人必须部署在获取 cookie 时的同一网络环境——这也是把扫码做进 TG（`/login`）而不是在别处扫码的原因。
3. 离线任务提交是同步的，大批量链接（>50 条）会较慢，后续可改为队列异步下发。
4. 尚未实现离线任务完成后的自动监控与重命名（原 115bot 的 `/mtask`、`/renameswitch` 等能力）。
5. `/d` 的真实上传已跑通（1MB / 3MB 实测均成功，SHA1 与 pick_code 双一致）。超过 5GB 的文件因 115 侧回调限制无法分片上传，会明确报错。
6. 上传吞吐受部署机器上行带宽限制，跨境部署时尤其明显，详见上文「速度提示」。
6. 境外机器访问 `qrcodeapi.115.com` 的 HTTPS 可能被 WAF 中断，扫码模块已内置「HTTPS 主域名 → HTTPS 备域名 → HTTP」降级。
